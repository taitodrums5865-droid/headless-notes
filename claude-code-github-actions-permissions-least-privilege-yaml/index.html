Claude Code GitHub Actions permissions come in two layers. The first is the Claude GitHub App, which needs Contents, Issues and Pull requests set to read and write. The second is the permissions: block in your workflow, which scopes the GITHUB_TOKEN and must include id-token: write for the action's default authentication. On top of those, claude_args: --allowedTools decides which tools Claude can actually run, and your Anthropic credential sits in a GitHub secret. Below you'll find the exact YAML for review, scheduled and code-writing jobs, plus a least-privilege table built from the official Claude Code GitHub Actions docs.

Key points

  • id-token: write is required for the default Claude GitHub App auth
  • Bash is off by default; allow only named commands in claude_args
  • Fork PR runs get no secrets; never check out PR head into root

Best for: Solo builders automating PR review and recurring jobs

What permissions does Claude Code GitHub Actions need?

It needs two things: the Claude GitHub App and a workflow permissions: block that includes id-token: write. The app needs Contents, Issues and Pull requests set to read and write. The app and the workflow token are two separate systems, and most permission confusion comes from mixing them up.

The first layer is the Claude GitHub App. The docs state the action "relies on three of the app's permissions": Contents, Issues and Pull requests, all read and write (Claude Code docs). When you install the app you actually grant a bigger set, because the app is shared with Code Review and web auto-fix. It includes Actions (read and write), Checks (read and write), Workflows (read and write), Repository hooks (read and write) and several read-only scopes. You can't trim that set: "GitHub doesn't let you accept a subset" (Claude Code docs). If that's a problem for you, the docs point to building a custom GitHub App with only Contents, Issues and Pull requests. That app works for the action only, though. Code Review and web auto-fix still need the official app.

The second layer is the workflow's GITHUB_TOKEN scopes. These come from the permissions: key at workflow or job level. GitHub's rule is strict: "If you specify the access for any of these permissions, all of those that are not specified are set to none" (GitHub workflow syntax). So once you write a block, list every scope you need.

The id-token: write scope is easy to miss. The official example labels it "required for the Claude Code GitHub Action's default GitHub App authentication" (Claude Code docs). Without it you get OIDC errors, as the action FAQ explains.

Two limits apply whatever you grant. Per the FAQ, the app has no workflow write access through the action, so Claude won't edit .github/workflows/. It also won't rebase, merge or force-push, even if you allow Bash(git rebase:*), because that rule lives in its system prompt (action FAQ).

How do you set a least-privilege permissions block for Claude Code?

Start with read-only scopes plus id-token: write. Add contents: write, pull-requests: write or issues: write only for jobs that change code or post with the GITHUB_TOKEN. The Claude Code docs and the security doc give 4 example blocks, and they show how far apart the needs are.

Here's the interactive block as the docs publish it, set at job level:

jobs:
  claude:
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
      actions: read

A few things trip people up:

  • Job-level vs workflow-level. GitHub accepts permissions "for an entire workflow or for individual jobs" (GitHub Docs). Put it on the Claude job so that other jobs in the same file don't inherit write access.
  • Missing actions: read. If you want Claude to read CI failures, you need the actions: read scope and the action input additional_permissions: "actions: read", which is "for viewing workflow results" (usage.md).
  • Using write-all for convenience. That gives the token every scope. The docs' own advice is to "grant the GITHUB_TOKEN the least required access" (GitHub Docs).

If you also run Claude headless on your own machine, the same mindset applies to local settings. See our headless permissions template.

How do you use allowed_tools and claude_args in Claude Code GitHub Actions?

In v1 of Claude Code GitHub Actions, tool limits and every other CLI flag go through claude_args (usage.md). The old allowed_tools input is deprecated. Pass --allowedTools with the specific tools and Bash patterns the job needs.

The old input is marked "DEPRECATED: Use claude_args with --allowedTools instead" (usage.md). The claude_args input "accepts any Claude Code CLI argument" (Claude Code docs), including --max-turns, --model, --mcp-config, --allowedTools (alias --allowed-tools) and --debug.

Defaults matter here. "The Bash tool is disabled by default for security" (action FAQ). For a plain-text automation prompt, the docs say Claude "has no shell or GitHub API access until you grant the tools the prompt needs" (Claude Code docs). So you're starting from a closed position and opening what each job needs.

Here is a multi-line claude_args example. Replace <model-id> with a model ID your account can use. This article doesn't recommend a specific model ID.

claude_args: |
  --model <model-id>
  --max-turns 8
  --allowedTools "Read,Edit,Bash(npm test:*),Bash(npm run lint:*)"

Common mistakes and fixes:

  1. **Bash(npm:*) is wider than it looks.** It covers npm install and npm publish as well as npm test. Name subcommands when you can. Our allowed-tools syntax guide covers how the pattern matching works.
  2. Review posts nothing. Either the --comment argument is missing from the review prompt, or claude_args doesn't name the inline-comment MCP tool. Without --comment, "Claude posts nothing" and findings stay in the run log (Claude Code docs).
  3. Still using @beta keys. direct_prompt, mode, max_turns and model are beta-era inputs. Move them to prompt and claude_args. The custom_instructions input becomes --append-system-prompt (upgrade section).

You can also pass tool rules as JSON through the settings input with a permissions.allow rule, if you'd rather keep them in a settings file (Claude Code docs).

How do you store the Anthropic API key safely as a GitHub secret?

Save the credential as a GitHub Actions secret and reference it only as ${{ secrets.NAME }}. Name it ANTHROPIC_API_KEY (or CLAUDE_CODE_OAUTH_TOKEN for a subscription token). The action's security doc puts it bluntly: "Never hardcode your Anthropic API key or OAuth token in workflow files!" (security.md).

These are the steps for a repository secret, using GitHub's UI labels (GitHub Docs):

  1. Open the repo and click Settings (or the More dropdown if Settings isn't shown).
  2. In the sidebar's Security section, click Secrets and variables, then Actions.
  3. On the Secrets tab, click New repository secret.
  4. Enter ANTHROPIC_API_KEY as Name, paste the key from the Claude Console as Secret, and click Add secret.
  5. In the workflow, add anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }} under with:.

For a subscription token, run claude setup-token locally, save the output as CLAUDE_CODE_OAUTH_TOKEN, and use the input claude_code_oauth_token instead. The docs list it for Pro, Max, Ultra, Team and Enterprise plans (Claude Code docs).

If you want a human gate on the riskier workflows, use an environment secret. Go to Settings → Environments, pick the environment, and under Environment secrets click Add secret (GitHub Docs). Then add environment: <name> to the job and set protection rules for that environment, described in GitHub's "Managing environments for deployment" page.

Pitfalls:

  • Sharing an OAuth token across an org. The docs recommend a Console API key for shared secrets, since an OAuth token is tied to the subscription of whoever ran claude setup-token.
  • Thinking deleted means revoked. Deleting the GitHub secret leaves the credential valid. To retire it, also delete the key in the Console (Claude Code docs).
  • Leaking via logs. show_full_output is off by default, and the security doc warns that logs "are publicly visible in GitHub Actions for public repositories!" (security.md). Leave it off unless you're debugging a private repo.

How do you set up an unattended PR review workflow with Claude Code?

Run the official code-review plugin on a pull_request trigger with read-only scopes. Add id-token: write to the workflow scopes and a claude_args line that allows only the inline-comment tool. This is the official example, with two optional additions marked in comments:

name: Code Review
on:
  pull_request:
    types: [opened, synchronize, ready_for_review, reopened]
    paths:            # example addition: only review source changes
      - "src/**"
jobs:
  review:
    runs-on: ubuntu-latest
    timeout-minutes: 15   # example addition: cap runaway runs
    permissions:
      contents: read
      pull-requests: read
      issues: read
      id-token: write
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          plugin_marketplaces: "https://github.com/anthropics/claude-plugins-official.git"
          plugins: "code-review@claude-plugins-official"
          prompt: "/code-review:code-review --comment ${{ github.repository }}/pull/${{ github.event.pull_request.number }}"
          claude_args: '--allowedTools "mcp__github_inline_comment__create_inline_comment"'

The base file, including actions/checkout@v6, fetch-depth: 1 and claude-code-action@v1, comes from the Claude Code docs, "Run a skill".

Steps:

  1. Install the Claude GitHub App on the repo.
  2. Add the ANTHROPIC_API_KEY secret (previous section).
  3. Save the file as .github/workflows/claude-code-review.yml on a branch and open a PR. That PR should trigger the first review.
  4. Check the run under the Actions tab, then look for inline comments on the PR.

Some behavior is built in. Claude skips draft and closed PRs, PRs it judges trivial or automated, and PRs that already have a Claude comment. On public repos, the docs note GitHub withholds secrets from fork PRs, "so the review runs only on pull requests from branches in the same repository" (Claude Code docs).

To limit by branch, add branches: [main] under pull_request. That matches the PR's base branch. Put your review criteria in CLAUDE.md and keep the file short, because Claude reads it on every run. Our CLAUDE.md template for unattended agents has a structure you can copy.

If you'd rather not maintain a workflow at all, Anthropic's separate Code Review product runs reviews without a workflow file.

How do you run Claude Code on a schedule or on issues without babysitting?

Give Claude Code a prompt (automation mode) on schedule or issues triggers. Pair it with narrow scopes, --max-turns and timeout-minutes so each run is bounded. Use @claude mentions (interactive mode) only when a human starts each request.

Here's a bounded nightly example, adapted from the official daily report. The concurrency, timeout and turn cap are example additions:

name: Daily Report
on:
  schedule:
    - cron: "0 9 * * *"
concurrency:
  group: claude-daily-report
  cancel-in-progress: true
jobs:
  report:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    permissions:
      contents: read
      issues: read
      id-token: write
    steps:
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: "Generate a summary of yesterday's commits and open issues"
          claude_args: |
            --max-turns 6
            --allowedTools "mcp__github__list_commits,mcp__github__list_issues"

Scheduling has some catches. GitHub runs scheduled workflows "only from the default branch," and in public repos it disables the schedule after 60 days without repository activity (Claude Code docs). Scheduled runs are attributed to whoever last changed the cron line. If that user is a bot, the human-actor check rejects the run unless the bot is in allowed_bots.

Loops are the other trap. If your workflow posts a comment containing @claude using GITHUB_TOKEN, nothing triggers, because "The github-actions user cannot trigger subsequent GitHub Actions workflows" (action FAQ). That's GitHub preventing infinite loops on purpose, so keep it. If you need chaining, use your own app token rather than widening allowed_bots to '*'. For machine-side scheduling outside GitHub, see our cron job setup guide.

Is it safe to run Claude Code on pull requests from forks or untrusted users?

Only with tight limits, because PR bodies, issues and comments can carry prompt injection. The defaults help: fork runs get no secrets, and non-write users are blocked.

GitHub's rule: "With the exception of GITHUB_TOKEN, secrets are not passed to the runner when a workflow is triggered from a forked repository" (GitHub Docs). That's why a plain pull_request review simply doesn't run on forks. Switching to pull_request_target to get fork coverage changes the risk. The security doc warns that pull_request_target and workflow_run "execute with the base repository's secrets" (security.md).

The core rule is short: "Do not check out an untrusted ref into the workspace root before this action" (security.md). On PRs, the action restores Claude config paths like .claude/, .mcp.json and CLAUDE.md from the base branch. The security doc notes that files such as package.json, lockfiles and Makefile stay at the PR head. Our inference from that is that an allowed command like npm test, which runs scripts defined in package.json, would execute whatever the PR author wrote there.

The action strips HTML comments, invisible characters and hidden attributes before Claude sees them, though the doc admits "new bypass techniques may emerge." On public repos, include_comments_by_actor lets you allowlist whose comments reach Claude. For more rule ideas, see our guardrails examples.

Should you use an Anthropic API key or OIDC (Bedrock/Vertex) for Claude Code GitHub Actions?

An Anthropic API key secret is the simplest choice for solo builders. OIDC through Bedrock, Vertex, Foundry or Anthropic workload identity federation avoids long-lived keys but needs cloud-side setup.

For federation, set anthropic_federation_rule_id (fdrl_...) and anthropic_organization_id. You can optionally add anthropic_service_account_id (svac_...) and anthropic_workspace_id. The docs say the action needs id-token: write for that exchange "even when you pass your own github_token" (Claude Code docs). Bedrock setups typically store an AWS_ROLE_TO_ASSUME secret, which is a role ARN, not a key.

How do you cap cost and runaway runs in Claude Code GitHub Actions?

Cap Claude Code GitHub Actions cost with --max-turns, job timeout-minutes, concurrency groups and narrow triggers, plus a cheaper model for routine work. Each run uses both GitHub Actions minutes and Claude tokens (Claude Code docs).

The default ceiling is generous. GitHub's job timeout is "The maximum number of minutes to let a job run before GitHub automatically cancels it. Default: 360" (GitHub workflow syntax). That's six hours of runner time if a run wanders. Setting timeout-minutes: 10 to 20 on review and report jobs is a reasonable starting point (example values; tune to your repo).

The concurrency option means "cancel any currently running job or workflow in the same concurrency group" (GitHub workflow syntax). For PR review, group by PR number: group: review-${{ github.event.pull_request.number }}.

On pricing, API runs bill per token at the rates on Claude's pricing page. With an OAuth token, runs draw on your subscription instead, and current plan prices are listed on the same pricing page. Subscription use is still subject to plan usage limits, so a busy repo may hit them. To see where tokens go, read our token usage guide.

Why is Claude Code failing with permission errors in GitHub Actions?

Most Claude Code GitHub Actions permission errors come from one of five causes. Either a scope is missing from permissions:, the Claude GitHub App isn't installed, the trigger user lacks write access, a tool isn't in --allowedTools, or a github_token was passed by mistake.

A quick diagnostic order:

  1. Open the failed run under Actions and find the first red step.
  2. If the error mentions OIDC or token exchange, check permissions: first.
  3. If Claude ran but did nothing useful, rerun with --debug in claude_args (private repos only, given public logs).
  4. Test the API key locally with claude before debugging YAML further, as the docs suggest.

Next steps

If maintaining workflow files isn't the route you want, there are two alternatives.

Anthropic's Code Review runs automatic PR reviews without YAML. It suits teams that only want review. It doesn't suit you if you need cron jobs, issue-to-PR automation or custom tool lists. It also requires the official Claude GitHub App with its full permission set (Claude Code docs). If cost predictability matters more than per-token billing, a Claude Pro or Max subscription with CLAUDE_CODE_OAUTH_TOKEN is another route. Plans are listed on Claude's pricing page. It's a poor fit for org-wide shared secrets.

FAQ

Does Claude Code GitHub Actions need id-token: write?

Yes, with the default Claude GitHub App authentication. The action uses the workflow's OIDC token to get its app token, and the action FAQ says you "must add the id-token: write permission." Anthropic workload identity federation needs it too, even if you pass your own github_token (Claude Code docs).

Can Claude Code push commits or open PRs from a workflow?

It can push commits to a branch (prefix claude/ by default) when the job has write scopes. But "Claude doesn't create PRs by default." It posts a link to a pre-filled PR page so a human opens the PR and branch protection still applies (action FAQ).

Should I pin the claude-code-action to a commit SHA?

The official examples use the moving @v1 tag, which picks up fixes automatically. You can see it in examples/claude.yml and the workflows in the Claude Code docs. GitHub's security hardening guide says pinning an action to a full-length commit SHA is the only way to use it as an immutable release. That makes a SHA the safer choice for workflows that hold write scopes or secrets. The trade-off is that you have to bump it yourself. By the same guidance, a branch ref like @main changes with every commit, so avoid it in production workflows.

Can I use Claude Code in GitHub Actions without an API key?

Yes. You can use a CLAUDE_CODE_OAUTH_TOKEN from claude setup-token on a Claude subscription. You can also use Anthropic workload identity federation, or OIDC with Amazon Bedrock, Google Cloud's Agent Platform or Microsoft Foundry (Claude Code docs). Each option still needs the Claude GitHub App or a custom app for GitHub access.
