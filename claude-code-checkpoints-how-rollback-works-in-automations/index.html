In interactive Claude Code, checkpoints are on by default. You undo with /rewind or by pressing Esc twice (Checkpointing docs). Headless runs (claude -p or the Agent SDK) have no one to press that key, so you have to turn file checkpointing on, save a checkpoint UUID and session ID from the output stream, and have your script call rewindFiles() / rewind_files() or run claude -p --resume <session-id> --rewind-files <checkpoint-uuid> when a check fails (Agent SDK file checkpointing). Rewind only restores edits made with Claude's Write, Edit and NotebookEdit tools. Bash changes, most subagent edits and directory operations are not covered (Agent SDK file checkpointing; Checkpointing docs), so you still need git as your main safety net in unattended jobs.

What a checkpoint is and what it isn't

Interactive Claude Code takes a checkpoint each time you send a prompt that starts a turn. It keeps file snapshots for the 100 most recent checkpoints in a session and stores them with the conversation, so /rewind still works after you resume (Checkpointing docs). The rewind menu can restore code, the conversation, or both, and it can also summarize part of the conversation (same source).

These limits matter more when nobody is watching:

  • Bash changes are not tracked. rm, mv, cp, sed -i or echo > file run through Bash can't be undone by rewind (Checkpointing docs; SDK docs).
  • Subagent edits usually aren't restored. The one exception is a skill with context: fork running in the foreground. For everything else the docs say to use git (Checkpointing docs).
  • Directories aren't undone. Rewind restores file content only. It doesn't reverse creating, moving or deleting directories. It also ignores remote and network files (SDK docs).
  • Symlinks and hard links are skipped. From v2.1.216, these paths are skipped and counted in skippedLinks (SDK docs).
  • Snapshots expire. By default they are deleted about 30 days after the session last saved one. After that a rewind can fail with "No files were restored". cleanupPeriodDays changes the retention period (Checkpointing docs).
  • Checkpoints don't replace version control. Anthropic describes them as "quick, session-level recovery" and recommends git for permanent history (Checkpointing docs).

The fileCheckpointingEnabled setting turns these snapshots on or off. Checkpointing is on by default (Settings reference).

How headless checkpointing differs

In the Agent SDK, checkpointing is opt-in. You need two options (SDK docs):

PurposePythonTypeScript
Track file changesenable_file_checkpointing=TrueenableFileCheckpointing: true
Get checkpoint UUIDs in the streamextra_args={"replay-user-messages": None}extraArgs: { "replay-user-messages": null }

With both set, each user message in the response stream has a uuid you can use as a restore point. Rewinding to the first user message's UUID returns tracked files to their original state (SDK docs). File rewinding doesn't rewind the conversation; the history stays as it was (same source).

The official examples also set permission_mode="acceptEdits" so edits go through without a prompt, which an unattended job needs (SDK docs).

Pattern 1: Rewind inside the run when validation fails

Use this when your script can tell during the run that something has gone wrong. For example: a test command fails, a protected file changes, or the diff is much larger than expected.

The docs' "checkpoint before risky operations" pattern keeps the most recent user-message UUID and calls rewind_files() as soon as your own condition is true, while the stream is still open (SDK docs). Here is a condensed Python version. should_revert() is a placeholder for your own check:

options = ClaudeAgentOptions(
    enable_file_checkpointing=True,
    permission_mode="acceptEdits",
    extra_args={"replay-user-messages": None},
)

first_checkpoint = None
async with ClaudeSDKClient(options) as client:
    await client.query("Update dependencies and fix type errors")
    async for message in client.receive_response():
        if isinstance(message, UserMessage) and message.uuid and not first_checkpoint:
            first_checkpoint = message.uuid
        if should_revert(message) and first_checkpoint:   # your own check
            await client.rewind_files(first_checkpoint)
            break

For automations, two practical decisions:

  1. Pick which checkpoint to rewind to. The docs' version overwrites the variable on every turn, so it only keeps the latest one. That undoes the last step. An unattended job usually wants to discard the whole attempt, so the example above keeps the first UUID.
  2. Call rewind before the loop ends. If you call rewindFiles() after you've finished iterating, you get "ProcessTransport is not ready for writing", because the connection closes when the loop completes (SDK docs).

Pattern 2: Record IDs now, rewind later

Often you only find out a run was bad after it ends. CI goes red an hour later, or a teammate reviews the diff the next morning. In that case:

  1. Save checkpoint_id and session_id for every run. A small JSON log next to your job output is enough. The docs show capturing session_id from the ResultMessage (SDK docs).
  2. Rewind later by resuming with an empty prompt. Open a new client with enable_file_checkpointing=True and resume=session_id, send "", and call rewind_files(checkpoint_id) inside the response loop (SDK docs).
  3. Or rewind from the shell. No SDK code is needed:
CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING=true \
  claude -p --resume <session-id> --rewind-files <checkpoint-uuid>

--rewind-files doesn't appear in claude --help, but the CLI accepts it. When it works, it prints Files rewound to state at message <checkpoint-uuid> and exits without sending a prompt (SDK docs). Without the environment variable, the bare CLI fails with "File rewinding is not enabled" (same source).

For example, a nightly job could save the IDs, and a separate "revert last night's agent run" script could read them and run the command above. Run the rewind on the same machine and project. Checkpoints belong to the session that created them (SDK docs), and the snapshots live in local Claude Code state (Checkpointing docs).

Using only the CLI, without the SDK

If your automation is a shell script, note that --replay-user-messages requires both --input-format stream-json and --output-format stream-json (CLI reference). You can also give the session a known ID up front with --session-id <uuid> (CLI reference). That way you don't have to parse the session ID from the output.

The SDK only sets CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING internally when checkpointing is enabled, and the bare CLI never sets it (SDK docs). Since "No file checkpoint found" can mean checkpointing wasn't enabled on the original session (same source), the safe reading is to set the variable on the original run too, not just on the rewind. The docs don't spell out this CLI-only flow end to end, so it's an inference. Test it on a throwaway repo before you rely on it.

An example launch, with the input message format to check against the headless docs:

SID=$(uuidgen | tr 'A-Z' 'a-z')
echo '{"type":"user","message":{"role":"user","content":"Fix lint errors in src/"}}' | \
CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING=true claude -p \
  --session-id "$SID" \
  --input-format stream-json --output-format stream-json --verbose \
  --replay-user-messages --permission-mode acceptEdits \
  > run.jsonl
CHECKPOINT=$(jq -r 'select(.type=="user" and .uuid) | .uuid' run.jsonl | head -1)
echo "$SID $CHECKPOINT" >> agent-runs.log

Don't use --no-session-persistence on runs you might want to rewind. That flag stops sessions being saved to disk, so they can't be resumed (CLI reference), and rewinding later depends on resuming.

Rewind vs. git vs. worktrees: which to use when

Checkpoints are one layer of protection. For unattended work, combine them with tools that cover what checkpoints miss.

MechanismCoversMissesBest for
Checkpoint rewindWrite/Edit/NotebookEdit changes to local files (SDK docs)Bash changes, most subagent edits, directories, symlinks, network filesFast, precise undo of the agent's own edits, including a return to a middle turn
Git commit/branch before the runEverything in the repo that git tracksUntracked/ignored files unless you include them; anything outside the repoThe baseline you can always reset to
--worktree / -wIsolates the run in <repo>/.claude/worktrees/<name> (CLI reference)Side effects outside the repo (APIs, databases)Recurring jobs that should never touch your main checkout
Permission limitsBlocks risky actions up front, e.g. --disallowedTools "Bash(rm *)", --permission-prompts none (CLI reference)Mistakes made with allowed toolsKeeping the agent's damage within what rewind and git can undo

How to decide:

  • If the job mostly edits files, checkpoint rewind is the cleanest undo. Keep a git commit underneath anyway.
  • If the job runs shell commands that change files (formatters, codemods, package managers), treat rewind as partial at best and rely on git or a worktree.
  • If the job uses subagents, assume rewind won't restore their edits, as the docs warn (Checkpointing docs).
  • If you need to undo a run days later, check that the snapshots haven't expired (about 30 days by default) and adjust cleanupPeriodDays if needed (Checkpointing docs).

A practical setup checklist

  1. Start each run on a clean git state, or in a worktree with claude -w <name> (CLI reference).
  2. Turn on checkpointing (enableFileCheckpointing / enable_file_checkpointing, or the env var for the bare CLI) and replay-user-messages (SDK docs).
  3. Save the first user-message UUID and the session ID for every run.
  4. Cap runaway runs with --max-turns and --max-budget-usd, both print-mode only (CLI reference).
  5. Add a validation step (tests, lint, diff-size check) and rewind automatically when it fails.
  6. After any rewind, run git status. Anything still changed came from Bash, a subagent or a skipped link. Reset it with git.
  7. Check skippedLinks in RewindFilesResult and alert on it, because those files kept their current contents (SDK docs).
